# 检索与引用设计（借鉴 WeKnora 的落地方案）

> 状态：设计稿（待评审）
> 目标：让「学习文档 + 记忆」进入可检索的知识层，回答带来源、可追溯、可评测。
> 原则：先 M1（零新依赖），M2 再考虑本地向量；不改动现有的三区 prompt 缓存契约。

## 1. 目标与非目标

### 目标

1. 把学习文档（大纲/进度表/笔记/疑问本）、章节、长期记忆统一切成可检索的知识块。
2. 检索升级为 BM25 关键词 +（M2）稠密向量，再加 LLM 重排，替代现在的纯 `LIKE` 子串打分。
3. 聊天回答能在正文标出引用编号，前端提供来源抽屉，用户能回到原文。
4. 保留现有「三区前缀缓存」设计：检索结果只进波动区尾部，不破坏稳定区/低频区指纹。

### 非目标

- 不做多租户、RBAC、IM 渠道、对象存储等 WeKnora 企业能力。
- M1 不做向量模型与向量库。
- M1 不做「AI 自动改写笔记 / 自动勾选章节」，只做检索与引用；写入能力仍属于学习模式阶段 B。
- 不做 PDF 全文 OCR、图片 VLM、音频 ASR。

## 2. 现状盘点（与方案相关的部分）

- 记忆检索：`memory.retrieve_facts` 用 `_tokenize`（英文/数字 + CJK 片段 + 2-gram）做 `in` 命中计数，预算 600 token。注释已写明「FTS5/向量是升级路径」。
- 学习文档：`notes/<project_id>/*.md` 四份文件 + `learning_notes_meta` 元数据；`learning_chapters` 有标题/目标/状态；`learning_questions` 有疑问/概念/出处。
- 对话注入：`prompt_builder.build_prompt` 的尾部顺序是 `volatile_text → 检索记忆 → 当前消息`，检索结果天然落在波动区尾部。
- SSE：`/api/chat` 已下发 `start / params / tool / delta / done` 事件，`done` 已带 `usage / message_id / version_group`。
- 前端：Markdown 由 marked + DOMPurify 渲染，聊天气泡下有工具提示与版本条，可复用 `renderMessageContent` 后的 DOM 遍历。

## 3. 总体架构

```
写入侧                              查询侧
──────────────────────────        ──────────────────────────
笔记/大纲 md ─┐                    用户问题
记忆条目 ─────┼─ 分块 ─ knowledge_chunks
章节/疑问 ────┘        │               │
                        ▼               ▼
                    FTS5(BM25)     查询构造(分词)
                    + 元数据          │
                                       ▼
                              BM25 召回 topK=15
                                       │
                              （M2 加 dense 向量，RRF 融合）
                                       │
                                       ▼
                              LLM 重排(DeepSeek，可关)
                                       │
                                       ▼
                              预算截断 ≤1200 token
                                       │
                                       ▼
                              【知识来源】注入波动区尾部
                                       │
                                       ▼
                              模型输出带 [1][2] 引用
                                       │
                                       ▼
                              done 事件下发 sources → 前端抽屉
```

两阶段：

- M1：FTS5 BM25 + LLM 重排 + 引用 UI，**零新依赖**。
- M2：可选本地 dense embedding（BGE-small-zh 等，经 ONNX 运行），RRF 与 BM25 融合；需要用户确认依赖体积。

## 4. 数据模型（SQLite）

### 4.1 知识块表

```sql
CREATE TABLE IF NOT EXISTS knowledge_chunks (
  id            TEXT PRIMARY KEY,          -- k + uuid8
  source_type   TEXT NOT NULL,             -- note / memory / chapter / question
  source_id     TEXT NOT NULL,             -- 原对象 id（重建索引用）
  project_id    TEXT,                      -- 学习项目，可空
  conversation_id TEXT,                    -- 记忆条目所属会话，可空
  title         TEXT DEFAULT '',           -- 文档名 / 章节名 / 事实标签
  heading       TEXT DEFAULT '',           -- 笔记里的标题路径
  content       TEXT NOT NULL,
  tokens        INTEGER DEFAULT 0,
  ordinal       INTEGER DEFAULT 0,         -- 同源内的顺序
  updated_at    TEXT
);
CREATE INDEX IF NOT EXISTS idx_kb_source ON knowledge_chunks(source_type, source_id);
CREATE INDEX IF NOT EXISTS idx_kb_project ON knowledge_chunks(project_id);
```

### 4.2 FTS5 外部内容索引

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS knowledge_fts USING fts5(
  content, title,
  content='knowledge_chunks',
  content_rowid='rowid',
  tokenize='trigram'
);
```

说明：

- `trigram` 支持中文任意 ≥3 字的子串匹配，英文词匹配也正常；2 字查询用 `LIKE` 兜底。
- FTS5 用外部内容表：`knowledge_chunks` 增删后执行 `INSERT INTO knowledge_fts(knowledge_fts) VALUES('rebuild')` 或按行触发同步。
- 如果运行环境的 SQLite 没有 FTS5/trigram（本机已确认 3.49.1 可用），自动退回 Python `LIKE` 检索，不影响主流程。

## 5. 索引内容与分块策略

| source_type | 来源 | 分块方式 |
|---|---|---|
| note | `notes/<pid>/*.md` 四份文档 | 按 `#` 标题切段，段内按空行/句号补切到 240–360 字，重叠 40 字；`title=文件名`，`heading=标题路径` |
| memory | `memory_items`（kind=fact，layer ∈ core/longterm） | 一条记忆一块，`title=层名`，原文不切 |
| chapter | `learning_chapters` | 标题 + 目标 + note 合成一块，`title=章节标题` |
| question | `learning_questions` | 疑问 + 概念 + 出处合成一块，`title=挂起疑问` |

暂不索引：

- 会话原文 `messages`（会爆炸且已有滚动摘要，M2 再评估）。
- 附件正文（当前已直接注入波动区，重复索引没有收益）。

## 6. 索引生命周期

### 6.1 写入钩子（新数据）

| 事件 | 钩子 |
|---|---|
| 学习项目创建成功 | `learning_skill.create_project` 写完 4 份 md 后调用 `knowledge.reindex_notes(project_id)` |
| 记忆新增/编辑 | `/api/memory` 的 POST/PUT 路由调用 `knowledge.reindex_source("memory", memory_id)` |
| 记忆删除 | DELETE 路由调用 `knowledge.delete_source("memory", memory_id)` |
| 章节/疑问落库 | 内部创建时调用 `knowledge.reindex_source(...)`（当前无外部写入 API，先内部覆盖） |

所有钩子都是**同步、幂等**的：按 `source_id` 先删旧块再重建，不锁聊天请求。


## 7. 查询管线（M1）

新增模块 `app/knowledge.py`，对外一个入口：

```python
async def search(
    query: str,
    provider,
    *,
    project_id: str | None = None,
    enable_rerank: bool = True,
    top_k: int = 15,
    budget_tokens: int = 1200,
) -> list[dict]:  # 每个结果带 score / source / excerpt / tokens
```

### 7.1 查询构造与 BM25

1. 复用 `memory._tokenize(query)` 得到英文词、CJK 段、2-gram。
2. 组装 FTS5 查询：
   - ASCII 词 → 加双引号的 phrase，`OR` 连接；
   - CJK 段 ≥3 字 → phrase；
   - 2 字段 → 单独走 `content LIKE '%xx%'` 兜底（FTS5 trigram 对 2 字不命中）。
3. 两类结果去重合并；FTS5 分数用 `bm25()` 归一化，LIKE 命中加固定加分。
4. 过滤：`project_id`（学习对话只搜本项目 + 全局记忆）与可选 source_type。

### 7.2 LLM 重排

- 条件：provider 是 DeepSeek 且 `enable_rerank=True`，候选数 > 1。
- 一次非流式调用：给模型 `[1]..[15]` 片段，要求输出 `{"scores":[87,12,...]}`；`thinking_enabled=False`，`max_tokens≈500`。
- 解析失败、超时、MockProvider → 保持 BM25 顺序。
- 预算：按重排分数从高到低取块，累计 token 不超过 `budget_tokens`。

目标延迟：BM25 <10ms；重排 +0.3–1.5s（可关）。

## 8. Prompt 与缓存分区

### 8.1 注入位置

在 `build_prompt` 的尾部、`retrieved`（记忆）之后、`current` 之前插入一条 system 消息：

```text
【知识来源】回答时可引用以下资料。引用处写 [编号]，编号必须与来源编号一致；
没有用到的资料不要引用；禁止编造编号。

[1] 来源：学习笔记「Python 学习大纲」> 第 3 章 函数
    内容：……
[2] 来源：长期记忆「用户偏好」
    内容：……
```

为什么放这里：稳定区 + 低频区不变 → 前缀缓存继续命中；知识内容随问题变化，本来就属于波动区。

### 8.2 参数面板新增

- 「知识检索」开关（默认开）：关闭时不检索、不注入来源。
- 「智能重排」开关（默认开）：关闭时只用 BM25 顺序。
- 「检索阈值」可选（M1 先固定为「无来源时静默降级」）。

### 8.3 与学习项目上下文的关系

`learning_skill.context_text` 仍然负责「项目总览」（大纲、进度、疑问摘要），新管线负责「按问题命中具体片段」。两者都在波动区，前者常驻、后者按需。

## 9. 引用与来源 UI

### 9.1 SSE done 事件扩展

```json
{
  "event": "done",
  "sources": [
    {
      "id": "k123",
      "ref": 1,
      "source_type": "note",
      "title": "Python 学习大纲 > 第 3 章 函数",
      "excerpt": "……",
      "project_id": "p1",
      "score": 91
    }
  ]
}
```

### 9.2 正文引用渲染

`renderMessageContent` 完成后，对 `.content.md` 的文本节点做一次遍历（跳过 `pre/code`）：

- `[数字]` → `<button class="cite" data-ref="n">[n]</button>`；
- 点击引用 → 弹出片段 + 来源类型 + 来源名；
- 提供「查看全文」：学习文档跳到左侧学习面板对应 tab；记忆跳到记忆面板。

### 9.3 来源抽屉

- 聊天头部新增「来源」按钮，当前 AI 回复有 sources 时显示数量徽标。
- 抽屉列表：类型图标（📖 学习文档 / 🧠 记忆 / ❓ 疑问 / 🕸 联网）、标题、命中片段、分数。
- 无来源命中：不显示按钮，回答正常输出。

### 9.4 调试与评测入口

- `GET /api/knowledge/search?q=...&project_id=...` 返回 top 结果与分数，前端数据面板可加「检索自检」。
- M2 再做固定问题集的 recall hit rate / BLEU / ROUGE 评测页。

## 10. 降级与回退

| 场景 | 行为 |
|---|---|
| FTS5 不可用 | 退回 `LIKE` + 命中打分（等于今天的能力，只是换成统一入口） |
| 无 DeepSeek Key | 跳过重排，保持 BM25 顺序 |
| 重排输出不是 JSON | 忽略重排，BM25 顺序 |
| 检索零命中 | 不注入【知识来源】，不传 sources，正常回答 |
| 知识表为空 | 懒索引补建；补建失败只影响本次检索，不阻断聊天 |

## 13. 需要你拍板的决策点

1. **M1 先做无向量方案**：确认接受「BM25 + DeepSeek 重排」先上线，而不是一步到位向量检索？
2. **重排成本**：每次知识问答多一次 LLM 调用（+0.3–1.5s 与少量 token），默认开还是默认关？
3. **M2 依赖**：本地 embedding 要装 `onnxruntime` 并下载 100–400MB 模型，是否能接受（Gili 一直是零依赖原型）？
4. **引用样式**：倾向「行内 [1]」还是「句末小圆点引用」？
