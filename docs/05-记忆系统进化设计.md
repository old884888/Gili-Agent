# 记忆系统进化设计（L1 相关检索 + 双段注入 + 可选工具式检索）

> 版本：v1.0（设计定稿）｜日期：2026-08-06｜状态：**阶段 A 已实施并验收通过**（阶段 B 待启用）
> 前置阅读：docs/01-设计文档.md（三层记忆）、docs/04-开发日志.md（现状）

## 1. 背景与问题

**用户核心担忧**："记忆一多，每次对话都拖家带口"——每轮请求把所有记忆都带上，token 膨胀、缓存失效、上下文被无关内容污染。

**现状的三个短板**：

| # | 短板 | 表现 |
|---|---|---|
| 1 | 弱检索 | 事实注入按"重要度+新鲜度"排序截断，与用户当前问什么**无关**——事实 ≥30 条后，600t 窗口可能全是无关事实 |
| 2 | 无相关注入 | 问跑步问题时带的是最新一批编程事实 |
| 3 | 缓存矛盾（隐藏） | 若简单引入"每轮按问题检索"，检索结果每轮变 → 低频区每轮变 → 缓存每轮失效——**检索不能进低频区** |

## 2. 现状盘点（基线）

```
存储：SQLite（messages 原文 / memory_items 事实+摘要 / conversations / request_logs）
提示词三区：
  稳定区  Soul(~32t) + 技能片段(~100t)          永远不变
  低频区  本会话摘要(~300t) + 事实条目(≤600t)    重写才变
  波动区  本会话历史(≤12k) + 环境注入 + 当前消息   每轮增长
固定记忆开销 ≈ 630t（预算 12k 的 5%）
```

## 3. 设计目标与原则

1. **相关优先**：记忆注入跟随"用户当前在问什么"，而不是"什么最新/最重要"
2. **缓存友好**：记忆检索不得伤害前缀稳定性（同话题连续命中、换话题才失效一次）
3. **容量可控**：固定开销维持 ~630t；检索注入按需 +200~600t；总占比 <10%
4. **渐进实现**：零新依赖起步（LIKE 子串匹配），jieba/FTS5/向量作为升级路径

## 4. 核心设计一：双段注入（缓存友好的关键）

把"记忆注入"拆成两段，各自进不同的区：

```
低频区（固定，缓存永远保住）       波动区尾部（随问题变化，本来就在增长端）
├─ 本会话摘要                        └─ 检索命中的普通事实（importance 1-2）
├─ importance=3 的事实（人格级）         按需注入，无命中则不注入
└─（几乎不动 → 指纹稳定 → 命中）
```

**缓存行为分析**：

| 场景 | 检索结果 | 前缀 | 缓存 |
|---|---|---|---|
| 连续追问同一话题 | 不变 | 不变 | ✅ 命中 |
| 换话题 | 变化 | 波动区尾部变 | ⚠ 失效一次（合理：确实在问新东西） |
| 检索无命中 | 不注入 | 不变 | ✅ 命中 |
| 用户编辑记忆 | 常驻区变 | 低频区变 | ⚠ 失效（已有记账机制） |

## 5. 核心设计二：L1 关键词检索（零依赖）

### 5.1 检索流程

```
用户消息 → 轻量分词 → 候选词表 → SQLite LIKE 子串匹配事实条目
        → 排序（命中词数 → importance → 新鲜度）→ 预算截断（600t）→ 注入波动区尾部
```

### 5.2 分词（v1 零依赖）

- 英文：按空白/标点切词，长度 ≥2
- 中文：提取连续 CJK 片段，长度 ≥2 的整段 + 2-gram 拆分为候选
- 停用词表：的/了/吗/呢/我/你/是/在/什么/怎么/为什么…（内置 ~50 词）
- **决策记录**：v1 不引入 jieba——事实条目几百条时全表 LIKE 是毫秒级，索引无必要；jieba/FTS5 是事实上万条时的升级路径（见 §10）

### 5.3 匹配与排序

- 匹配：`content LIKE '%词1%' OR ...`（对 content 做子串匹配，命中事实条目）
- 排序：命中词数降序 → importance 降序 → created_at 降序
- 截断：注入总 token ≤ 600（与现状预算一致，可配）

### 5.4 兜底

- 无命中 → 不注入（省 token）
- 命中但全部是 importance=3（已在常驻区）→ 去重后不重复注入

## 6. 核心设计三："翻记忆"工具（第二阶段，可选）

**定位**：自动检索的补充——模型主动调用的深挖工具，核心价值是**省 token**（结果只在需要时进上下文）。

```
工具定义（随请求进稳定区，像 web_search 一样）：
  search_memory(query) → 返回匹配事实（内容+重要度+时间）
触发场景：用户明确问"你还记得我之前说的 X 吗"、模型觉得自动注入不够
开关：记忆面板/设置可关（省 token）
```

**何时启用**：事实库事实上千条、自动检索成本变高时（当前几百条自动检索已覆盖，工具式先设计后启用）。

## 7. 数据模型变更

- `memory_items` 无结构变更（content / importance / created_at 已够用）
- 可选预留：`topic` 主题标签列（分组展示用，本期不做）

## 8. API 与 UI 变更

**API**：
| 接口 | 说明 |
|---|---|
| `GET /api/memory/search?q=xxx` | 手动搜索事实条目（记忆面板搜索框） |
| chat 请求体 | 无需变更（后端按消息自动检索） |

**UI（记忆面板）**：
- 顶部加**搜索框**（调 /api/memory/search）
- 事实条目按"常驻（⭐3）/ 可检索"徽标区分（可选）

## 9. 性能与容量承诺

| 指标 | 数值 |
|---|---|
| 固定记忆开销 | ~630t / 预算（5%） |
| 检索注入 | 按需 +200~600t，无命中 0 |
| 500 条事实 LIKE 检索 | <10ms |
| 检索对缓存影响 | 同话题 0 影响；换话题失效 1 次 |

## 10. 实施计划

### 阶段 A：L1 相关检索 + 双段注入（✅ 已实施，2026-08-06）
1. `memory.py`：`_tokenize`（零依赖分词）+ `retrieve_facts`（LIKE 匹配+排序）；`get_context` 三返回值（summary / fixed_facts ⭐3 / retrieved_facts）
2. `prompt_builder.py`：`build_prompt` 增加 `retrieved` → 【相关记忆】注入波动区尾部
3. `main.py`：chat 组装检索结果进波动区；`/api/memory/search`；memory/usage 反映新分段
4. 记忆面板搜索框（回车/按钮搜索，清空恢复）
5. 验收：单测 5 项通过（排序/去重/尾部注入/指纹稳定/搜索接口）

### 阶段 B：工具式检索（视事实规模启用）
1. `search_memory` 工具定义 + 执行器（复用 L1 的检索函数）
2. 稳定区工具定义 + 技能开关（"记忆检索"技能或并入现有）
3. 探测轮集成（与 web_search 同一机制）

## 11. 验收标准

- [ ] 问"我之前说过我学日语吗" → 回答引用相关记忆（而非最新记忆）
- [ ] 同话题连续 3 轮 → 缓存命中率不降（数据面板核对）
- [ ] 换话题 → 失效 1 次后恢复命中
- [ ] 注入 100 条测试事实后，检索延迟 <10ms、每轮固定开销不变
- [ ] 检索无命中时零注入、零失效

## 12. 未来演进（不做，记录在案）

- **L2 向量检索**：本地嵌入模型（bge-small-zh + sqlite-vec）——事实万条级时启用
- **时间衰减**：importance × 0.99^days——个人陪伴场景收益低，暂缓
- **主题分组**：抽取时打 topic 标签，记忆面板按主题折叠
- **记忆合并**：定期把同主题冗余事实合并（agentmem consolidate 模式）
